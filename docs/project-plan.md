## 3. 已确认的设计决定

| 主题 | 已确认决定 |
| --- | --- |
| 平台 | Web 平台，桌面和移动端都要支持。 |
| 网格 | 保持旧版六边形网格与“每格最多一支棋子”的基本规则。 |
| 回合 | 玩家按座位/序号严格依次行动；每位玩家固定经历“行动 → 加点”两个阶段。无合法行动自动进入加点，点数用完自动进入下一玩家行动。 |
| 队伍 | 队友只共享胜负关系；单位、点数、行动权仍归各自玩家。 |
| 友伤 | 默认关闭；准备房间由房主设置 `friendlyFire`，开局时写入本局地图状态。 |
| 结束回合 | 可手动结束行动/加点；所有单位无合法行动时自动进入加点，点数用尽时自动轮到下一玩家。手动结束加点会保留未使用点数。 |
| 房间与地图位 | 地图声明可参战玩家位；房间不设置成员人数，观战者不占地图位。至少一名参战者且所有参战者准备即可开局。 |
| 位置 | 固定模式选择具体地图位；随机模式只选择参战/观战，开局时从全部地图位中随机抽取位置。 |
| 空地图位 | 未分配给参战者的位置不生成初始单位，相当于开局已无军队；是否立即结束仍由地图胜负模块决定。 |
| 临时身份 | 首次访问随机生成本地名字并持久化，开始前可修改；该名字作为房间成员显示名，但不等于正式账户。 |
| 地图预览 | 准备房间直接用只读 `HexBoard` 渲染当前地图状态，确保地形、单位和贴图与正式棋盘同源。 |
| 地图配置 | 内置首图名为「昏晓」；首版作者可导入、查看、复制经过验证的 JSON 地图码，数据保存在当前浏览器，暂不做可视化编辑。房主在准备房间选图后，房间同步完整地图码给所有成员。 |
| 页面往返 | 无房间号时默认进入主页；邀请链接仍直接进入指定房间。地图配置、房间入口、准备房间和对局均可回主页；离开联网房间需释放连接并移除 URL 中的房间号。 |
| 计时 | 步时从玩家行动开始，行动与加点共用，操作不会重置；进入加点至少保留 2 秒。局时按各玩家累计扣减，耗尽即强制结束该玩家当前回合，此后该玩家每回合有 2 秒行动与至少 2 秒加点。步时不大于局时；任一为 0 表示该项不限时。 |
| 响应方式 | 当前联网模式由房主客户端执行 `game-core` 并广播权威快照；服务端绑定发送者地图位并中继命令，不重复执行棋盘规则。 |
| Mod 信任 | Mod/地图作者提交的代码默认可信，但仍要限制在定义好的 SDK 和运行时边界中。 |
| 可扩展性 | 地形、单位、规则、胜利条件均应可由代码扩展。 |

## 4. 地形、供电与收益模型

### 原则：能力组合，不写继承链

不采用“海洋继承 → 平原继承 → 据点继承”的类层级。地形和单位从公共能力池中选择能力；这样新增油田、电塔等时不需要修改既有父类。

```text
地形定义 + 能力模块 + 规则触发器
单位定义 + 能力模块 + 当前所在格
                    ↓
         公共规则计算派生状态
                    ↓
            游兵 / 通电兵等显示结果
```

### 首批能力模块

| 模块 | 作用 | 可用于示例 |
| --- | --- | --- |
| `occupiable` | 格子允许单位占据 | 海洋、平原、据点、可选油田 Mod |
| `power-conductor` | 此格可参与同队供电网络 | 平原、据点 |
| `power-source` | 作为电力网络起点 | 据点、电厂 |
| `income-source` | 按条件在结算时产生点数 | 可选油田 Mod、矿井 |
| `adjacent-hostile-exhaustion` | 被占据据点令相邻非同队单位在本回合耗尽行动力 | 据点 |

### “游兵 / 通电兵”定义

- 单位默认是游兵，即未获得供电网络状态。
- `power-network` 规则寻找同一玩家/同一队伍定义的供电源和可导电路径。
- 若单位满足连接条件，派生状态为通电兵；这个状态由规则计算，不能被客户端直接伪造。
- `core/powered-income` 是单位能力；基础游兵在拥有者行动回合开始时以通电状态产生 1 点，不依赖其所处地形。行动过程的地形/连通变化只影响下一次结算。
- 油田 Mod 可定义为“任意己方占据单位在下一轮产生 2 点”，不依赖供电。

### 不可进入格

单位必须绑定在一个带有 `occupiable` 能力的格子。山地与虚无在规则内核中完全等价：都没有 `occupiable`，因此任何单位都不能进入、停留或作为移动目标。两者若需要保留，只作为地图美术或作者标记，不增加不同的移动条件、单位白名单或额外规则模块。

### 据点封锁与回合状态

据点不等于供电系统：它通过组合能力同时拥有“被占据时供电”和“相邻敌方单位耗尽”两项独立逻辑。后者检查刚完成移动的单位是否落在被占据据点的六个相邻格；非同队单位会收到 `unit-exhausted` 事件，事件把其 id 写入当前回合的 `turn.exhaustedUnitIds`。行动判定只需检查该数组，因此不再有旧版全局 `inactivate` 集合散落在移动、战斗和回合代码里的问题。

据点自身所在格不在封锁范围；同队单位不受封锁。`friendlyFire` 只影响同队间能否攻击，不改变“同队”关系和据点封锁关系。

电力网络已确认按“同一玩家”连接，不跨同队队友。队伍只绑定胜负与友军关系；开启 `friendlyFire` 也不会改变供电归属。

## 5. 房间与联网响应模型

### 地图选择与页面导航

内置默认地图「昏晓」以版本化 JSON 地图码表示。地图库允许在当前浏览器保存自定义地图码、预览并复制；地图码包含名称、尺寸、地形图例、玩家位、初始单位、队伍和胜负条件。当前只能通过地图码导入，地图的可视化编辑、云端账户同步和发布仍属后续阶段。

房主创建房间后可从本机可用地图中选择。服务端校验地图码，将所选地图名称、完整地图码和玩家位数量广播给所有成员；其他成员即使没有在本机保存该地图，也能预览并按同一地图开局。切换地图会清除所有人的准备状态；超出新地图玩家位的成员转为观战。邀请链接继续直接进入房间；主动返回主页时离开当前房间并清除链接中的房间号。

### 准备房间

地图的玩家位和房间成员分别建模。`mapPlayerCount` 只限制参战者；观战成员不占地图位，当前 64 连接上限只是服务端传输保护，不是可配置游戏人数。成员状态包含参战/观战、具体地图位、准备、连接与房主标记，展示时参战者在前、观战者在后。

固定位置模式把地图位直接映射为 `player-1`、`player-2` 等玩家 ID；随机模式在开局时从全部地图位中随机抽取位置。只要至少一名参战者在线且全部准备，房间便自动开局。开局载入地图时，未分配位置的初始单位被清空，之后回合轮转跳过无单位玩家；房间层不额外假设“只剩一队”就是胜利，结算仍由地图选择的模块完成。

### 对局传输

非房主参战者只发送带 `expectedSequence` 的命令；服务端根据成员实际地图位覆盖行动者 ID，观战者的命令会被丢弃。房主用本地 `game-core` 执行命令并广播完整权威快照，其他客户端不自行确认结果。只有当前房主可以发布 `host-snapshot`。

`room-sync` 会补发身份与房间状态。若房间已经开局，新账户加入固定为观战者，服务端定向补发内存中的最新房主快照；原账户刷新则认回自己的座位，不生成重复成员。房主离开后由下一位在线成员接管最近的权威快照。

步时和局时由房主时钟推进：移动、攻击与加点不会刷新本回合步时；行动阶段结束后，加点阶段使用剩余步时且至少有 2 秒。每位玩家的累计局时仅在自己行动时扣减；耗尽时强制结束当前回合，此后每回合获得 2 秒行动与 2 秒加点。房主快照附计时余额和截止点；服务端重基准后转发，晚进观战与房主移交不会重置时间。未来若切换为服务端权威模式，可以复用已导出的无界面校验入口，但这不是当前部署方式。

## 6. Mod 与地图代码模型

每个 Mod 是固定版本的 TypeScript 包：

```text
mod.json               id、版本、SDK 版本、依赖与内容哈希
src/terrain.ts         地形定义和能力组合
src/units.ts           单位定义与行动规则
src/rules.ts           触发器、命令处理器与结算规则
src/victory.ts         胜利/失败条件
assets/                图标、音频、地图素材
```

地图保存时锁定 Mod 的 `id + version + contentHash`。这样 Mod 后续更新不会改变已经创建的地图或正在进行的对局。

初版 SDK 的规则处理器只能：读取当前状态、读取本次命令、使用引擎注入的可复现随机数、返回类型化事件。它不能依赖真实时间、网络请求或文件读写；目的不是限制可信作者，而是保证客户端预测、服务端校验、重放和观战结果完全一致。

可信 Mod 仍放入独立 Worker 执行单步规则，以便在死循环、异常或内存问题时终止该 Mod 而不让整台游戏服务崩溃。

- [x] 移动、基础攻击、行动耗尽状态。

- [x] 公共 `power-network` 模块：通电和连通区域变化。
- [x] 据点回合结算；油田回合结算由可选 Mod 提供。
- [x] 基础胜负条件：只剩一支队伍。
- [x] 六边形、供电、据点封锁、据点收益的单元测试。

**当前验收：** 规则内核可在不启动网页时通过 30 个测试；网页原型可完成本地两阶段回合。行动回合开始时结算当前玩家的通电单位/油田收益，行动期间的变化留待下次结算。游兵行动后的兵力衰减、一点兵的本回合失活，以及油田离开时生成的留守游兵，都由规则内核的统一结算入口写入 `turn.exhaustedUnitIds`。游兵攻击后的失活由独立的 `core/exhaust-after-attack` 能力控制；通电兵不受该规则影响，但进入已占据敌方据点的相邻格时仍优先失活，空据点和友方据点不触发。无可行动单位时自动进入加点，最后一点投入后自动进入下一玩家行动。棋谱三元组固定为 `[行, 列, 点击次数]`：成功移动/攻击只写入用户实际点击的手动选中源格和目标格，各为 `1`；自动续选、试选、取消和非法点击均不记录。连续对同一格加点会合并累计次数。`[-1,-1,-1]` 与 `[-1,-1,-2]` 分别记录两种结束操作。每次动作另保留独立续选坐标，服务端持久化和回放播放器仍待补充。

### 阶段 A.1：当前本地原型的临时战斗规则

本地预览实现的是可互动的规则切片，用于验证架构、状态和界面，并非旧版攻击公式的最终复刻：

- `core/move`、`core/attack`、`core/attack-range`、`core/counterattack`、`core/counterattack-limit`、`core/action-strength-decay`、`core/exhaust-after-attack`、`core/powered-action-threshold`、`core/powered-income` 是相互独立的单位能力；兵种可按需组合，而非继承某个固定兵种。
- 基础游兵的 `core/powered-action-threshold.minimumStrength` 为 2，故通电兵只有 1 点时无论移动或攻击都不能行动；`core/powered-income.amount` 为 1，故每个通电兵在拥有者加点阶段开始时产生 1 点。
- 基础游兵的 `core/action-strength-decay` 配置为“行动结果减 1、最低保留 1”：游兵行动前为 1 点时不再扣点，但会在本回合失活；通电兵移动时仍在原格保留 1 点，并在目标格生成扣除后的其余兵力。移动只可落在空的可驻兵格。
- 油田不带导电能力；其 `core/departure-garrison` 会在占据者离开时，于油田生成 1 点 `core/roamer`，并让这个留守兵在当前行动回合失活。油田只有 1 点兵时不能离开，以免凭空复制兵力。
- 攻击目标由独立攻击距离决定；默认关闭友伤，同队单位不是合法攻击目标。地图显式开启 `friendlyFire` 后才允许攻击队友。
- 近战攻击时，进攻兵力大于守方则占据目标格并保留差值；相等则双方消失；较小则只削减守方兵力。远程兵可配置攻击成功后不进入目标格。
- 防守单位具有 `core/counterattack` 时，在其自身 `core/counterattack-limit` 内可反击；当前临时公式以防守方剩余兵力削减进攻方。
- 基础游兵拥有 `core/exhaust-after-attack`，攻击完成后当前回合不能再次行动；通电兵跳过这条单位能力，因此可以继续攻击。
- 单位进入被敌方占据据点的相邻格，当前回合写入 `exhaustedUnitIds`，优先级高于攻击后的继续行动；空据点、友方据点和据点本身不触发。
- 当前玩家手动结束行动或所有单位均无合法行动后，进入自己的加点回合；收益已在该玩家行动开始时确定。最后一点投入后自动进入下一玩家行动；手动结束加点时未使用点数不会清零。
- 加点回合点击通电兵即投入 1 点；长按以三次方曲线逐渐加速，最多 3 秒投入该位置可用的全部点数。
- 动作返回与目标格分离的 `continuation` 单位/坐标；若其仍有合法行动，客户端自动续选。为兼容未来大炮等“不移动但攻击”的能力，不能将其一律视为目标格。

**需要确认：** 若希望严格复刻旧版的攻击差值、断电兵攻击补偿、破防、据点防御和加点阶段，请给我确认的文字规则或允许我继续按旧版代码逐条复刻。确认后会替换这套临时战斗结算。
