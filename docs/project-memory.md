# Numeral Lord 项目备忘录

这是项目的持久工作约定。开始新任务或发布前先读本文件；用户后续明确更改约定时，以最新指示为准。

## 发布环境与授权

- 默认发布目标是正式环境。只有用户明确说测试站、stage 或测试链接时，才发布到测试环境。
- 用户已明确：当前账号和对局都是测试用途；用户要求发布时可直接发布，不要仅因存在活动测试连接而停下或重复询问。重启 relay 可能让这些测试连接断开。
- 正式页面：`http://39.107.250.161/numeral-lord-play/`
- 正式 relay：`ws://39.107.250.161/numeral-lord`，服务器内部端口为 `2567`。
- 测试页面：`http://39.107.250.161/numeral-lord-play-stage/`
- 测试 relay：`ws://39.107.250.161/numeral-lord-stage`
- `pnpm --filter @numeral-lord/web build:deploy` 只会在本地构建 `dist`，不会上传或发布。必须明确完成远端发布和发布后健康检查，不能把构建说成部署。

## SSH 登录

SSH 私钥是自定义文件名，位于 `C:\Users\z\.ssh\numeral_lord_deploy_rsa`。连接时显式使用：

```powershell
ssh -i C:\Users\z\.ssh\numeral_lord_deploy_rsa -o IdentitiesOnly=yes -o BatchMode=yes root@39.107.250.161
```

如果未指定 `-i` 的默认连接失败，不代表没有密钥或服务器无法访问；先用上面的身份文件重试。私钥内容绝不可输出、复制进仓库或放入归档。

## 正式部署

- 正式部署脚本：`deploy/update-production.sh`。
- 远端脚本要求发布包放在 `/tmp/numeral-lord-next-production.tar.gz`，项目路径为 `/opt/numeral-lord-next`。
- 脚本会构建完整候选版本、保留服务器工坊资源目录和 PostgreSQL 数据，再切换代码并重启 `numeral-lord.service`。旧目录和发布包只在切换期间临时存在；健康检查成功后立即删除，只保留当前运行版本。健康检查失败时自动恢复旧版本并清理候选版本。
- 脚本本身按安全策略检查 `2567` 活动连接，但用户已说明当前都是测试账号、要求直接发布。按用户当前授权执行，不因测试连接阻塞；发布前仍须确认归档范围中无密钥、`.env`、本地数据库、`node_modules`、构建缓存等敏感或无关文件。
- 发布后核对正式页面 HTML/JS/CSS、贴图资源和 relay 健康，并按变更运行合适的双客户端烟测。
- 测试环境脚本：`deploy/update-staging.sh`；同样只保留当前运行版本，不积累回滚目录。不得把它误认为正式发布。

## 长期架构约束

- 不存在内置 Mod 的需求。核心运行时代码不得捆绑、预装或默认依赖某个具体 Mod；Mod 定义以服务器数据库中的当前记录为准，客户端仅在运行期间载入内存，不长期保存 Mod 或版本副本。
- 用户名称（NFKC 规范化、去首尾空格、大小写不敏感）是工坊账号的唯一查找键：数据库有该名称就复用原 `user_id`，没有才创建；同名跨设备得到同一 `user_id`。这是名称映射，不是经过验证的登录凭据，不能作为安全认证。
- Mod 订阅状态保存在服务器数据库并绑定上述 `user_id`。订阅仅决定地图编辑器的可选地块；读取已有地图、加入房间和开始对局都按地图中的 Mod ID 从服务器取当前定义，不要求每台设备订阅或版本一致。
- 玩家个人地图（已保存/导入的地图，不含未保存编辑草稿）保存在服务器数据库并绑定 `user_id`；浏览器只保留按规范化玩家名称隔离的本地缓存及离线待同步操作。连接工坊后由数据库快照协调缓存，同名玩家换设备可恢复；旧的浏览器全局地图缓存只迁移一次到当前玩家账号。个人地图删除也必须同步到数据库，避免跨设备复活。
- 浏览器不再把 Mod 定义、订阅或已安装版本存进 IndexedDB。唯一例外是升级清理旧客户端数据时的一次性兼容步骤：可读取旧订阅并提交服务器，收到服务器确认后删除旧 IndexedDB；它不是当前运行时存储。
- 每个 Mod ID 只有一个当前定义；发布更新时替换数据库中的当前记录，不维护对局用的不可变版本历史或精确版本锁。
- 通用地图码解析器不得硬编码具体 Mod ID，也不得把旧地图中的字符猜测成某个 Mod 地形（例如 `F → mod/oil-field`）。地形含义必须来自地图码自身明确提供的 `terrainLegend`，并按服务器当前 Mod 目录解析。
- 不兼容无版本的旧地图对象，不做静默升级或猜测式迁移；遇到缺失/不支持的地图码版本时明确报错。未来如确需迁移，必须先有明确的格式规范和用户可理解的显式迁移流程，不能把临时错误或历史偶然约定固化为运行时兼容规则。
- 2026-10-05 用户明确要求导入原版 Base64 + zlib 二进制地图码。此转换仅在网页地图导入入口执行，按原版 v1 的字段规范生成当前 v1 JSON；导出、账号同步和通用地图解析仍使用显式版本 JSON，不接受无版本 JSON，也不猜测 Mod 地形。仅导入基础地形、非零兵力单位、玩家名称、队伍和九色旗帜；原版玩法、电脑和计时由当前系统配置。原版从下向上编号且奇数行右移，当前棋盘从上向下编号且偶数行右移；转换时反转行，奇数行数地图同时反转列，全部格子和单位同步重排以保留六边形邻接。
- Mod 可以出现在隔离的测试夹具或 Mod 自身示例中，用于验证从服务端当前定义加载后的行为；这不构成核心内置 Mod 或默认地图。测试示例必须使用显式版本、地形图例和 Mod 依赖，不能通过旧字符映射暗中加载。

## 主页视觉与跨端响应式原则

- 主页是后续页面跨端设计的视觉参考。按桌面、手机横屏、手机竖屏三种实际使用场景分别安排布局密度和内容优先级，不要只把桌面页面等比缩小。
- 入口页三个入口始终并排三列；窄屏优先收缩装饰图形、辅助文案和卡片间距，不能退化成竖排，也不能让整页滚动成为默认操作。
- 不保留“选择入口”这类重复标题；三个可操作入口本身就是清晰的导航。
- 优先使用首屏空间，避免内容挤成屏幕中央的小岛、过大的空白装饰框或无效留白；若空间不足，先收紧组件内部布局，再让明确的内容面板内部滚动。
- 每次响应式 UI 修改都要检查桌面宽屏、常见横屏和窄竖屏的实际渲染，确认关键文字可读、触控目标可用、浮动控件不遮挡内容，并检查文档没有意外横向或纵向溢出。
