# Numeral Lord 架构审查

审查基线为 `2be9b1a`。共享规则内核和工作区分层适合继续沿用。面向公开用户时，应优先解决账号与席位身份、对局裁决权和个人地图的跨设备一致性。

## 文件结构

| 目录 | 职责 |
| --- | --- |
| `apps/web` | Vue 路由与页面、Pixi 棋盘、联机、地图库和工坊 |
| `apps/server` | Colyseus 房间与大厅、联机协议、工坊和账号数据访问 |
| `packages/game-core` | 状态、命令、六边形网格、规则结算和模拟接口 |

| `deploy`、`docs` | 运行、部署和架构约定 |

## 前端

- **组件边界。** 审查时 `WorkshopPanel.vue` 约 1,732 行、`HexBoard.vue` 约 1,331 行、`LobbyPanel.vue` 约 967 行、`MapEditor.vue` 约 673 行。优先按可单独理解和验证的界面职责拆分工坊与大厅。页面和父容器持有跨区业务状态，子组件通过 props 接收数据、通过 emits 上报交互。组件的归属、状态和样式边界见[前端组件说明](frontend-components.md)。
- **运行时职责。** 懒加载路由和常驻应用壳有利于跨页面保留房间连接。`useAppRuntime` 同时处理重连、命令同步、地图操作、Mod 加载和棋盘交互。后续可按房间会话、工坊及地图同步、棋盘控制拆出具有独立生命周期的模块。参考 [应用运行时](../apps/web/src/app/app-runtime.ts)。
- **棋盘性能。** Pixi 棋盘已有分层和编辑器增量渲染，常规绘制仍扫描全图。地图上限 4,096 格，后续用真实手机对大图、复杂贴图和连续操作测帧耗时，再依据数据调整绘制范围。参考 [棋盘实现](../apps/web/src/components/HexBoard.vue) 和 [地图解析](../packages/core-content/src/map-code.ts)。

## 应用底层

- 前端、服务端与 AI 可以共用 `getLegalIntents` 和 `applyIntent`。保留规则内核独立性，并用同一组合法命令序列验证浏览器源码入口与 Node 编译入口的一致性。
- 引擎用对象身份缓存供电、合法目标和空间查询。状态和内容目录需要按不可变快照使用，热更新应替换对象。
- 声明式 Mod 规则有空间查询预算。最大地图叠加复杂 Mod 时，应度量整条命令的耗时。工坊按既定约定只保存当前定义，若未来需要复算历史战报，可在对局产物保存开局规则和引擎版本。
- [旧架构基线](architecture-baseline.md)与[项目备忘录](project-memory.md)在同步和存储描述上存在差异。后续应更新基线，使其对应实际命令复制、数据库同步和 Mod 生命周期。

## 审查验证

前端 142 项、后端 102 项、规则内核 85 项测试通过，三者类型检查和前端正式路径构建通过。Windows 沙箱阻止 pnpm 依赖检查创建链接，以上验证使用已安装工具直接运行。线上环境、真实 PostgreSQL 跨端场景、双客户端烟测、移动端性能和独立 AI 实验未纳入该次审查。
